# zipnative v0.9.0

<!-- GitHub Release title: v0.9.0 — final pre-freeze RC -->

_Released 2026-09-02_

The final pre-freeze release candidate. The last additive API wave before the 1.0 freeze — `verifyZip()` one-call verification, `ReadableStream` sources everywhere a stream goes in, entry-attribute helpers — plus a full-project coverage pass: the untested branches are tested, the sample corpus grows to 33 archives (hostile refusals included), the recipe set to 12, and the playgrounds to 5 with CDN-first engine loading. The Zip64-streaming design is recorded as a decision, not shipped. **100% backward-compatible with v0.8.2 — no archive-byte changes; deterministic bytes unchanged; no new error codes.** Zero runtime dependencies, 77 exports across the two entry points. Tagged in git; not published to npm — v1.0.0 is the first npm publication.

## Highlights

- **`verifyZip()` — one call, a machine-readable verdict.** Deep validation (eager structure + per-entry CRC/size/local-header checks + collected diagnostics) returning a `ZipVerificationReport` that **never throws for archive problems**: structural refusals land in `report.error` with the frozen `err.code` vocabulary, and encrypted or stream-only-codec entries are reported as `skipped` with a reason — never faked as corruption. The agent-facing archive inventory the roadmap promised.
- **`ByteSource` widening** — `iterateZipEntries()` and `addStream()` (worker subpath included) now accept a Web `ReadableStream<Uint8Array>` as well as any `AsyncIterable<Uint8Array>`: `fetch` bodies and `File.stream()` work directly, no wrapping.
- **Entry-attribute helpers** — `isSymlinkEntry()` and `getUnixMode()` (`number | null`, null when the entry was not authored on a Unix host — an explicit null-vs-0 contract).
- **Coverage closed out** — ~24 new tests reach the branches no suite exercised (custom codecs end-to-end, deflate-tier injection, the buffered `addStream` fallback, the Zip64-streaming refusal, the pure inflate pump, strict parity across all five entry points); six hostile sample archives are now generated under *inverse* validation (generation aborts unless the exact expected refusal fires).
- **Playgrounds 3 → 5, CDN-first** — new `modify` (save vs saveCompact, live dead-bytes diagnostic) and `stream` (chunked forward iteration, inflater byte counters, the trust caveat made visible) pages; all five load the engine from a version-pinned CDN (esm.sh → jsDelivr) with the committed local bundle as fallback, so they run the published package once it exists and keep working before then.

## Security

- **No parser/writer posture change.** `verifyZip` is composition of existing validated paths; the source widening normalises at one boundary and changes no parsing.
- **feat(samples):** the refusal corpus makes the security posture *demonstrable* — zip-slip, device-name, duplicate-path, overlap, CD-mismatch and declared-bomb archives ship as samples with a machine-readable manifest of their expected `err.code`, each generated under inverse validation.
- **feat(tests):** `extractZipStream` zip-slip parity and bit-3 `skip()` under limits are now pinned; the `ZIP_UNSUPPORTED_ZIP64_STREAMING` refusal is regression-tested instead of being an untested branch.

## Added

- **feat(parser):** `verifyZip` / `VerifiedEntry` / `VerifyZipOptions` / `ZipVerificationReport` (new "Verifying" export category).
- **feat(core):** `ByteSource` (exported type) + one-boundary normalisation for `iterateZipEntries` and `ZipWriter.addStream`/`ParallelZipWriter.addStream`. A `ReadableStream` is always driven through `getReader()` (the native async iterator would *cancel* the stream on early exit; the contract is release-without-cancel), and `iterateZipEntries` closes its source on every exit path — the reader lock is released, the unread remainder stays the owner's to cancel or keep. Pinned by test.
- **feat(core):** `isSymlinkEntry` / `getUnixMode` (new "Entry attributes" export category); api.json now lists 77 exports.
- **feat(tests):** `tests/parser/zip-verify.test.ts` + `tests/integration/coverage-hardening.test.ts` (~24 tests).
- **feat(samples):** generators `refusals` (+ `refusals.json` manifest), `parallel` (SHA-256 IDENTICAL verdict), `forward-trust`, `attributes`, incremental dead-bytes — corpus 22 → 33 archives.
- **feat(docs):** recipes `verify-archive`, `resumable-inflate`, `custom-codec`, `parallel-create`, `sanitize-external-sink` — 7 → 12.
- **feat(docs):** playgrounds `modify.html` and `stream.html`; the shared CDN loader (`load-engine.js`, version-pinned by `docs:playground`, engine source displayed on every page).

## Changed

- **docs(release-notes):** the pdfnative release-note format adopted (template + all nine historical notes reformatted in place; `Known limitations` and `Downstream integration notes` stay as documented zipnative extensions).
- **docs(meta):** Zip64-streaming ADR recorded in the roadmap — per-entry `AddEntryOptions.zip64` opt-in retained as the design; implementation post-1.0 (the speculative local-header extra is the hard part); the typed refusal stays.
- **docs(meta):** README, quickstart, llms.txt and the playgrounds hub updated for the 0.9 surface.

## Install

Not published to npm — pre-1.0 versions are git tags (`git checkout v0.9.0`); the first npm publication is v1.0.0.

## Upgrade

No breaking changes. Drop-in replacement for v0.8.2.

## Known limitations

- store+bit3, encrypted+bit3 and custom-codec+bit3 remain refused in forward reading — structurally undelimitable without the central directory.
- Zip64 streaming (`addStream` > 4 GiB) remains a typed refusal — designed (see the roadmap ADR), implemented post-1.0.
- A worker playground is deliberately absent (the only page that would require build-tooling changes; logged post-1.0).
- zipnative.dev DNS/CNAME activation is a deployment step, not a repo artefact.

## Downstream integration notes

`verifyZip`'s report is the natural payload for a future `zipnative-cli verify --json`: it is machine-readable by construction (frozen codes, explicit `skipped` reasons) and never throws for archive problems, so the CLI's exit-code mapping can be a pure function of the report.
