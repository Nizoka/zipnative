# zipnative v0.5.0

<!-- GitHub Release title: v0.5.0 — workers & forward streaming -->

_Released 2026-09-01_

Milestone M4 — workers, parallelism and forward streaming; the last engine milestone before the API-freeze phase. The new `zipnative/worker` subpath fans per-entry deflate across a real worker pool with byte-identity to `createZip()` as a tested contract, and `iterateZipEntries()` reads unseekable streams forward without a central directory. **100% backward-compatible with v0.4.0** — `createZip` bytes are unchanged (goldens prove the behavior-frozen planning refactor). Zero runtime dependencies. Tagged in git; not published to npm.

## Highlights

- **`zipnative/worker`** — `createParallelZip()` fans per-entry deflate across a real worker pool: Node `worker_threads` and Web Workers, pool sized from available cores, worker script resolved by the library (with a `workerUrl` escape hatch for exotic bundlers). Output is **byte-identical to `createZip()`** per resolved compression tier — a tested contract, including through real worker threads.
- **`iterateZipEntries()`** — forward, central-directory-less reading of unseekable streams (pipes, uploads, serverless bodies) with bounded memory and every security limit enforced by output counting.

## Security

- **feat(security):** forward-reader trust caveat — `iterateZipEntries` trusts local headers alone: no central directory cross-checks names, sizes or methods, so hostile archives can present different content here than `openZip()` reports (the classic upload-scanner differential). The TSDoc, README, llms.txt and SECURITY.md all state it: use forward iteration only for streams you cannot seek. Names are not sanitized (`sanitizeEntryPath()` before any filesystem sink).
- **fix(security):** fuzzing caught a real bug during development — a truncated source could hang the `DecompressionStream` pump forever (reader awaiting input that never comes). Fixed by aborting the writable on write-side failure; the streaming-boundaries suite pins it. The hang never shipped.
- **feat(worker):** caller buffers are never detached (slice-before-transfer, asserted by test); infra failures never fail an archive.

## Added

- **feat(worker):** `createParallelZip` / `ParallelZipWriter` / `ParallelZipOptions` (subpath `zipnative/worker`; `toBytes()` is async there — the one honest signature difference).
- **feat(parser):** `iterateZipEntries` / `StreamedZipEntry` / `StreamedZipHeader` on the main entry.
- **feat(ci):** real-worker CI integration step (Linux + Windows, post-build); scheduled non-blocking bench trend workflow.

## Changed

- **refactor(core):** core planning refactored behavior-frozen (shared method rules, async planner, spec collector) — `createZip` bytes unchanged, goldens prove it.

## Install

Not published to npm — pre-1.0 versions are git tags (`git checkout v0.5.0`); the first npm publication is v1.0.0.

## Upgrade

No breaking changes. Drop-in replacement for v0.4.0.

## Known limitations

- `iterateZipEntries` refuses data-descriptor entries (flag bit 3) with `ZipUnsupportedError('cd-less-descriptor')` — their payload cannot be delimited safely without the central directory. **This includes archives produced by zipnative's own `addStream()` path, and by some common producers (bsdtar writes bit-3 archives — our own interop fixture confirmed it).** A resumable pure-TS inflater that lifts this is roadmapped (0.6.x).
- `setDeflateImpl`/`registerCodec` on the main entry do not propagate to the worker bundle (separate module state); byte-identity is promised for the built-in tiers.
- Benchmarks: no blocking CI gate by decision (shared-runner variance); `bench/RESULTS.md` is refreshed per minor on a documented machine — v0.5.0 numbers are unchanged from v0.2.0 for the existing scenarios (no read/write path changes).

## Downstream integration notes

For the future `zipnative-cli`: streaming input support should route seekable inputs to `openZip` and reserve `iterateZipEntries` for true pipes, surfacing the bit-3 refusal with the CLI's own remedy text.
